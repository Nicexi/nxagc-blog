几乎所有 AI 编码工具都支持一个"项目规则文件"：Codex 和许多 Agent 读取 `AGENTS.md`，Claude Code 读取 `CLAUDE.md`，Cursor 有 `.cursor/rules`。它会在每次会话开始时自动加载，相当于给 AI 的入职手册。

写得好，AI 从第一句话就懂你的项目和习惯；写得差，它就成了一份每轮都要付费、却没人遵守的长文。这篇文章分享我写规则文件的思路。

## 规则文件应该写什么

按优先级排序，我会写这几类内容：

1. **项目事实**：技术栈、目录结构、启动和构建命令。
2. **工作约定**：代码风格、命名、提交规范、哪些目录不能动。
3. **行为边界**：什么操作需要确认、修改范围、何时停止。
4. **交付要求**：完成时要报告什么、证据怎么给。

一个简洁的例子：

```markdown
# 项目说明

- 后端：server/，Node 22 + Express 5，数据库为 node:sqlite
- 前端：web/，React 19 + Vite
- 启动：npm run dev:server 与 npm run dev:web
- 构建检查：npm run build

## 约定

- 默认使用中文回复，代码和命令保留原文
- 只修改与任务直接相关的文件，不顺手重构
- 删除文件、修改数据库结构、提交和推送前先确认

## 交付

- 说明改了哪些文件及原因
- 区分已验证和未验证的部分，附上关键命令输出
```

## 写法上的几个原则

### 写行为，不写口号

"请认真负责地完成任务"对模型没有任何约束力。把它换成可执行的行为：

| 口号式 | 行为式 |
| --- | --- |
| 保证代码质量 | 修改后运行 `npm run build`，构建失败时修复后再交付 |
| 不要乱改 | 只修改用户点名的文件；需要扩大范围时先说明原因 |
| 结论要准确 | 结论附 `file:line` 或命令输出，推测要单独标注 |

### 写清楚优先级和冲突处理

规则多了难免冲突，比如"直接完成修改"和"破坏性操作先确认"。明确写出：用户的当前要求优先于默认流程，安全和授权要求优先于效率。

### 只写 AI 不知道的

模型已经知道怎么写 JavaScript，不需要你再教一遍语法。规则文件应该写**你的项目特有的东西**：这个仓库的目录约定、这个团队的提交格式、这个环境的特殊限制。

### 控制长度

规则文件每轮都会进入上下文，越长越贵，也越容易被稀释。我的经验是：

- 核心规则控制在一两屏以内；
- 只在特定场景需要的长篇说明，拆成单独文件或 Skill，按需加载；
- 定期删掉 AI 从来没违反过、或者已经过时的条目。

## 分层组织

大一些的项目可以分层：

```text
~/.config/agent/AGENTS.md    # 个人通用习惯：语言、交付格式
repo/AGENTS.md               # 项目级：技术栈、命令、约定
repo/server/AGENTS.md        # 子目录级：后端特有的规则
```

越靠近代码的规则越具体，通用规则不要在每一层重复。

## 用迭代代替一次写完

最好的规则文件不是一次设计出来的，而是从实际问题里长出来的：

1. AI 做错了一件事，先想是不是缺了信息还是缺了约束。
2. 用一两句行为式规则补上。
3. 观察后续几次任务是否还会出现。
4. 一段时间后回顾，合并重复条目，删除无效条目。

例如我发现 AI 经常在只问原因时直接改代码，就补了一条："诊断请求只调查和报告，用户明确要求修改时才写入文件。"这条规则之后，类似问题基本消失了。

## 小结

- 规则文件是给 AI 的入职手册，写项目事实、工作约定、行为边界和交付要求。
- 写可执行的行为，不写口号。
- 只写模型不知道的，控制长度，按需拆分。
- 从实际问题中迭代，定期清理。

一份好的规则文件，能让你少说很多重复的话，也能让 AI 在你没注意的时候依然守规矩。
