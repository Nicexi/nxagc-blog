如果你也做 AI 相关的开发，大概会有这种感觉：上个月刚把一套提示词调顺，这个月新模型出来，原来的技巧不灵了；刚学会某个框架的写法，社区已经转向了另一种范式；收藏夹里"稍后再读"的文章越来越多，真正读完的越来越少。

从 Prompt Engineering 到 RAG，从 Function Calling 到 Agent，再到 MCP、Skills、多 Agent 协作，每隔一段时间就有一个新概念被称为"下一个必学技能"。追得越紧越焦虑，不追又怕被落下。

这篇文章想聊聊：AI 发展快到学习成本这么高的时候，开发者应该怎么学，以及哪些东西可以放心不学。

## 为什么会这么累

学习成本高，不只是因为新东西多，而是几个因素叠在了一起。

**知识的半衰期变短了。** 过去学一门语言、一个框架，能用好几年。现在某个模型的提示技巧、某个工具的配置方式，可能几个月后就被新版本取代。投入同样的时间，回报周期短了很多。

**信息噪音太大。** 每个新发布都伴随着大量"颠覆""封神""xx 已死"的标题。真正有价值的变化，被淹没在营销和情绪里，筛选本身就要耗费大量精力。

**工具之间互不兼容。** 不同的 AI 编码工具有不同的规则文件、插件机制、上下文管理方式。换一个工具，很多经验要重新积累。

**害怕错过。** 看到别人用新工具效率翻倍，就担心自己落后。但很多时候我们看到的是精心挑选的演示，而不是日常的真实体验。

## 先分清：哪些会过期，哪些不会

面对快速变化，最重要的一步是把知识分层。变化快的那一层，不值得深挖；变化慢的那一层，才值得长期投入。

| 层次 | 例子 | 变化速度 | 投入策略 |
| --- | --- | --- | --- |
| 具体工具和产品 | 某个编辑器插件、某个 Agent 框架的 API | 很快，按月变 | 用到再学，学到够用为止 |
| 使用模式 | 提示词结构、RAG、工具调用、Agent 循环 | 中等，按年演化 | 理解原理和适用场景 |
| 底层原理 | 上下文窗口、Token、注意力的局限、模型为什么会出错 | 慢 | 值得系统学一次 |
| 通用工程能力 | 拆解问题、读代码、调试、写测试、设计接口、表达需求 | 几乎不变 | 长期投入，越用越值钱 |

你会发现，真正决定 AI 用得好不好的，往往是下面两层：知道模型的局限在哪，知道怎么把一个模糊的需求拆成清楚的任务，知道怎么验证结果对不对。这些能力不会因为换了模型就失效，反而会因为模型变强而更值钱。

## 策略一：问题驱动，而不是新闻驱动

最有效的过滤器是你手上的项目。看到一个新工具时，先问自己：

1. 它解决的问题，我现在遇到了吗？
2. 我现在的方法在这个问题上有多痛？
3. 换过去的成本是多少，能不能先在一个小任务上试？

如果三个问题都答不上来，就把它放进"观察列表"，而不是"学习列表"。大部分新东西，三个月后要么成熟了、文档齐全了，学起来更省力；要么已经没人提了，你省下了全部时间。

## 策略二：适度延迟采纳

技术圈有一个朴素的经验：**不要在第一时间重度投入新技术。** 对 AI 工具尤其适用。

新发布的东西通常有这些问题：文档不全、行为不稳定、最佳实践还没形成、过几周可能就有破坏性更新。等它经过一两个版本、社区踩完第一批坑之后再上手，学习成本往往能降低一大半。

延迟不等于忽视。可以花十分钟看一下官方介绍，知道它是什么、解决什么问题，然后等到真正需要时再深入。

## 策略三：建立自己的"评测集"

别人说某个模型或工具"强很多"，对你的场景未必成立。与其看评测文章，不如准备几个自己的固定任务：

- 一个你熟悉的 Bug 排查任务
- 一个中等复杂度的功能开发任务
- 一个需要读懂老代码的重构任务

新模型、新工具出来时，用同样的任务跑一遍，对比结果质量、耗时和成本。半小时就能得出比任何评测文章都可靠的结论：它对我到底有没有用。

## 策略四：用抽象层隔离变化

在代码层面，也可以降低"追新"的成本。把模型调用封装在一个清晰的边界后面，业务代码不直接依赖某个厂商的 SDK 细节：

```js
// 业务代码只依赖这个接口，不关心背后是哪个模型
export async function summarize(text, { maxLength = 200 } = {}) {
  return llm.complete({
    system: '用中文总结以下内容，不超过指定字数。',
    prompt: text,
    maxTokens: maxLength * 2,
  });
}
```

这样换模型、换供应商时，改动集中在一处。同样，项目的 AI 协作规则也尽量写成通用的行为描述，而不是绑定某个工具的特殊语法，换工具时大部分内容可以直接复用。

## 策略五：让 AI 帮你学 AI

学习成本高，有一部分是"读文档"的成本。这恰好是 AI 擅长的事：

- 让它对比新旧版本的变化，只列出和你项目相关的部分；
- 让它根据官方文档写一个最小可运行示例，你在示例上改；
- 遇到新概念，让它用你已经熟悉的东西做类比解释。

但要记住上一篇文章里说的：涉及具体 API 时，以官方文档和实际安装的版本为准，不要直接相信模型的记忆。

## 策略六：给信息源做减法

与其关注几十个账号、订阅一堆周报，不如只保留少量高质量来源：

- 你实际在用的工具和模型的**官方更新日志**；
- 一两个长期输出、有实际项目经验的作者；
- 你所在团队或社区里真实的使用反馈。

刷信息流的时间，拿来在自己的项目上做一个小实验，收获通常大得多。

## 策略七：把学到的东西写下来

每次踩坑、每次试用新工具，用几段话记下来：解决了什么问题，怎么配置，哪里有坑，最后用没用。

写下来有两个好处：一是逼自己把模糊的感觉变成清楚的结论；二是半年后工具又变了，你能快速判断哪些经验还有效。这也是我写这个博客的原因之一。

## 哪些事可以放心不做

最后列几件我认为可以放下的事，给自己减减负：

- **不必试用每一个新模型。** 等你的评测集告诉你值得换，再换。
- **不必掌握每一种 Agent 框架。** 理解 Agent 的基本循环（规划、调用工具、观察结果、继续）比熟悉某个框架的 API 重要得多。
- **不必收藏所有提示词技巧。** 很多技巧是在弥补旧模型的不足，新模型上可能已经不需要了。
- **不必为了"不落后"而焦虑。** 你今天没学的东西，大概率三个月后会有更简单的学法。

## 结语

AI 发展快，并不意味着我们要以同样的速度学习。追逐每一个新名词，最后得到的往往是一堆碎片化的印象；而把时间花在底层原理和工程能力上，换来的是面对任何新工具都能快速上手的底气。

工具会一直变，但把问题想清楚、把任务拆清楚、把结果验证清楚，这些能力不会过时。与其跑得更快，不如站得更稳。
