用 AI 写代码，账单和速度往往不取决于模型有多贵，而取决于你往上下文里塞了多少东西。一次对话里，模型每轮都要重新"读"一遍全部历史：系统提示、工具定义、读过的文件、命令输出、之前的回答。上下文越长，单轮成本越高，响应越慢，模型也越容易被无关信息带偏。

这篇文章整理了我在日常 AI 开发中节省 Token 的做法，核心只有一句话：**只给模型完成当前任务必需的信息。**

## 先搞清楚 Token 花在哪

一个典型的编码 Agent 会话，Token 大致来自四部分：

| 来源 | 特点 | 优化空间 |
| --- | --- | --- |
| 系统提示与工具定义 | 每轮固定发送 | 中，精简规则、按需加载工具 |
| 文件内容 | 单次可能上万 Token | 大，按行号、按符号读取 |
| 命令输出 | 日志、测试、构建输出极易膨胀 | 大，先过滤再返回 |
| 对话历史 | 随轮数线性增长 | 大，阶段性压缩、开新会话 |

多数人只盯着提示词写得长不长，真正的大头通常是**文件和命令输出**。

## 读文件：定位优先，别整文件灌进去

最常见的浪费是让 AI "看一下这个项目"，结果它把十几个文件完整读了一遍。更好的方式是先定位，再精读：

```bash
# 先找到符号在哪
rg -n "function createPost" server/src

# 只读需要的那一段
sed -n '120,180p' server/src/posts.js
```

给 AI 的指令也可以写得更具体：

> 只看 `server/src/posts.js` 里的 `updatePost`，以及它直接调用的函数。不要读其他模块。

明确的文件、符号和行号，比"帮我看看哪里有问题"省得多，也准得多。

## 命令输出：先过滤，再给模型

构建日志、测试输出、`npm install` 的进度条，动辄几千行，真正有用的可能只有几行报错。让 AI 执行命令时，养成在命令里截断的习惯：

```bash
# 只要错误和最后的结果
npm run build 2>&1 | grep -E "error|warning|built" | head -20

# 大 JSON 用 jq 取需要的字段
curl -s localhost:3000/api/posts | jq '.items[] | {id, title, status}'

# 日志只看最近且相关的部分
tail -n 200 app.log | grep -i "timeout"
```

如果你在搭建自己的 Agent 工具，也应该在工具层做截断：超过一定行数只返回首尾，并告诉模型完整输出保存在哪个文件里，需要时再按需读取。

## 对话历史：用摘要替换已经消化的内容

一个调查过程可能产生几十次工具调用，但结论往往只有几条。已经得出结论的部分，就不该原样留在上下文里：

- **阶段性总结**：一个子问题解决后，让 AI 用几行话记录"结论、证据位置、下一步"，后续基于摘要工作。
- **适时开新会话**：任务切换时（比如从排查 Bug 转到写新功能），开一个新会话，只带上必要的背景摘要。
- **不要反复重读**：已经确认过的文件和结论，不需要"为了保险"再读一遍。

很多 Agent 框架都提供了上下文压缩能力，原理相同：把消耗过的原始输出替换为摘要，保留可回查的索引。

## 用好提示缓存

主流模型服务都支持提示缓存（Prompt Caching）：如果请求的**开头部分**与之前的请求完全相同，这部分可以按更低价格计费，响应也更快。要让缓存生效：

1. 把稳定内容放在前面：系统提示、工具定义、项目规范。
2. 把变化内容放在后面：当前问题、最新的工具结果。
3. 避免在稳定前缀里插入时间戳、随机 ID 等每次都变的内容。
4. 不要频繁修改历史消息，一旦前缀变了，后面的缓存就全部失效。

这也意味着压缩历史并不是越频繁越好：每次压缩都会改写前缀，需要重新付费缓存。比较合理的节奏是**积累一批已消化的内容后再一次性压缩**。

## 子任务委派：用干净的上下文做脏活

需要大范围搜索、阅读大量资料时，可以把它交给一个独立的子 Agent：它在自己的上下文里读完所有材料，只把结论和 `file:line` 级别的证据交回来。主会话只需要承担几百 Token 的结论，而不是几万 Token 的原始材料。

委派时要把任务写完整，因为子 Agent 看不到主对话：

```text
目标：找出 server/src 下所有直接执行 SQL 的位置
范围：只读 server/src，不修改文件
输出：每处给出 file:line、SQL 用途、是否使用参数化查询
```

## 模型分级：不是每件事都需要最强模型

- 代码搜索、格式整理、生成样板代码：用速度快、价格低的模型。
- 架构设计、复杂 Bug 定位、跨模块重构：用推理能力强的模型。
- 思考强度（Reasoning Effort）同理，简单任务调低，能显著减少输出 Token。

## 一份可直接用的检查清单

- [ ] 指令里写明了文件、符号或目录范围
- [ ] 命令输出经过 `grep`、`head`、`jq` 过滤
- [ ] 已经得出结论的调查过程做了摘要
- [ ] 系统提示和工具定义保持稳定，没有动态内容
- [ ] 大范围调查交给子任务，只取回结论
- [ ] 简单任务用了便宜的模型或较低的思考强度

省 Token 和提升质量其实是同一件事：上下文越干净，模型越专注，答案也越可靠。
