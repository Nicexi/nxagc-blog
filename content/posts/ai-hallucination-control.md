在编码场景里，AI 的"幻觉"往往不是凭空编故事，而是更隐蔽的形式：调用一个不存在的 API，引用一个旧版本的参数，声称"已经修复并验证"但其实从未运行过，或者把推测当成事实写进结论。这些错误看起来都很合理，所以更危险。

幻觉无法被彻底消除，但可以通过流程把它压到很低，并让剩下的错误容易被发现。我的做法可以归纳为三条：**让模型有据可查、让结论可以复核、让不确定性说出来。**

## 幻觉从哪里来

理解原因才能对症下药。编码场景中最常见的几类：

1. **知识过期**：模型训练数据有截止时间，库的 API 早已变化。比如 React Router、Express 等大版本升级后，写法差异很大。
2. **上下文缺失**：模型没看到真实代码，只能"猜"项目里有哪些函数、字段叫什么。
3. **上下文污染**：会话太长，早期的错误假设、无关文件混在一起，模型抓错了重点。
4. **被期望驱动**：用户问"是不是 X 导致的"，模型倾向于顺着说"是"。
5. **完成压力**：模型倾向于给出"已完成"的答复，即使中间某一步失败了。

## 第一招：让模型先看材料，再下结论

最有效的防线是**事实来自工具，而不是记忆**。在给 AI 的规则里明确要求：

```markdown
- 结论必须以实际读取的文件、日志、配置或命令输出为依据
- 涉及第三方库的 API，先查看项目中安装的版本和类型定义
- 不确定的接口不要猜测，先查文档或源码
```

几个实用技巧：

- **查已安装的版本**：`npm ls express`、`cat node_modules/marked/package.json | jq .version`，比让模型回忆可靠得多。
- **看类型定义**：`node_modules/xxx/index.d.ts` 是最准确的 API 文档。
- **查官方一手资料**：库的 GitHub 仓库、CHANGELOG、官方文档，优先于博客和问答。

## 第二招：要求可复核的证据

让模型在结论里附上证据位置，幻觉会立刻变得显眼：

> 请给出每个结论对应的 `file:line` 或命令输出。没有证据支撑的部分，标注为推测。

一个合格的诊断应该能串起这样一条链：

```text
用户症状 → 实际输入与调用 → 实现中的错误位置 → 修复路径
```

链条中任何一环只有"应该是""大概率"，就说明还没查清楚。

## 第三招：区分事实、推断和未验证

要求模型在交付时把三类信息分开写：

- **已确认**：读过代码、跑过命令得到的结果。
- **推断**：基于已有材料的合理判断，但未直接验证。
- **未覆盖**：没有执行的运行时行为、没有检查的环境。

例如一份可信的交付说明：

```text
已确认：构建通过（vite build 输出 ✓ built）；接口 /api/posts 返回 200。
未验证：图片上传未在浏览器中实际操作；生产环境 HTTPS 下的行为未测试。
```

这比一句"已完成，一切正常"有用得多。**禁止 AI 把没跑过的东西说成"已验证"**，是我在规则里写得最重的一条。

## 第四招：别用问题诱导答案

对比两种问法：

- ❌ "是不是缓存导致页面不更新？"
- ✅ "页面在保存后不更新。请检查从保存请求到页面渲染的数据流，找出状态没有刷新的位置。"

前者让模型去证明一个结论，后者让模型去寻找原因。描述现象、提供日志，把判断留给证据。

## 第五招：控制上下文的干净程度

长会话里，错误假设会被模型反复"引用"，越说越像真的。几个习惯：

- 发现方向错了，明确告诉模型"排除 X 方向"，必要时开新会话并只带上已确认的结论。
- 大范围资料搜索交给独立子任务，主会话只接收结论和出处。
- 不要把大段无关日志贴进对话，先过滤出相关片段。

## 第六招：用编译器和运行结果兜底

模型可以说错，编译器和运行结果不会。代码改动之后，至少做与改动范围相称的检查：

```bash
# 语法与类型
node --check server/src/index.js
npx tsc --noEmit

# 构建
npm run build

# 实际请求
curl -s localhost:3000/api/posts | jq '.total'
```

这些检查的结果应该原样出现在交付里，而不是被总结成"检查通过"。

## 小结

| 幻觉类型 | 对策 |
| --- | --- |
| 编造 API | 查已安装版本、类型定义和官方文档 |
| 猜测代码结构 | 先读文件，结论附 `file:line` |
| 顺着用户说 | 描述现象，不预设结论 |
| 虚报完成 | 区分已确认与未验证，附命令输出 |
| 上下文污染 | 排除错误方向、阶段性摘要、开新会话 |

把这些要求写进项目的 AI 协作规范里，比每次对话临时提醒要稳定得多。
